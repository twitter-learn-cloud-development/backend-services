# 补充调查与证据缺口闭环

日期：2026-10-04。范围：用户端只读客服，本机交付；外部 Chat API 不变。

## 问题与链路

旧逻辑会永久累积历史任务的 gaps：即使补充任务找到了相关证据，也没有明确机制
证明它解决了哪一个原缺口。不能用任意新任务成功来清空全部历史缺口。

当前链路：运行时生成缺口编号 → 补充计划关联编号 → 执行只读任务 → 独立语义评估
及引用绑定校验 → 关闭被支持的目标缺口 → 聚合全部历史证据与剩余缺口 → 最终回答。

## 内部协议

- `EvidenceGap(gap_id, task_id, question)`：编号来自原任务 ID 与缺口描述的 SHA-256
  摘要，不依赖并行结果顺序，不接受 Worker 自报编号。同文案的不同任务保持隔离。
- `TaskSpec.resolves_gap_ids`：可选、默认空；首轮禁止引用，补充轮只允许当时开放的
  缺口，同轮重复分配拒绝。未关联的任务成功不会关闭其他任务的缺口。
- `SupportState.task_history`：保留首轮及所有已通过校验的补充任务定义。评估使用
  原任务的要求与成功标准，不以补充 Planner 改写后的标准替代。
- `GapResolution(gap_id, task_id, evidence_refs, rationale)`：仅由运行时接纳独立
  模型评估的结果；不是 Worker 自行宣称的解决状态，不返回给浏览器。
- `AggregatedResult.unresolved_gaps/resolved_gap_ids`：结构化开放/关闭状态；保留
  `unresolved_questions` 兼容旧提示和测试。成功任务带 gaps 也仍然存在缺口。

## 安全与降级

只有明确关联、实际成功、无新 gaps、含工具证据的任务可进入评估。独立评估提示
包含原问题、精确缺口、原任务要求及候选实际证据，要求核对对象、字段和时间。
每条评估必须关联已派发任务、目标开放 gap，且引用全部属于该任务工具证据；
未知、重复、跨任务或非法评估整体拒绝。Worker 返回错误 task_id 按失败处理。

存在证据冲突时不关闭缺口；关闭缺口也不删除历史证据或消除冲突。只有存在证据、
无冲突、无开放缺口才达到聚合器可回答条件。已关闭缺口对应的旧失败总结不混入
当前总结，最终 Composer 同时收到关闭记录，避免把历史失败当作当前状态。

每批候选至多一次额外模型评估；同补充任务仅评估一次，不执行无限修复。
异常、非法 JSON、评估拒绝时保留开放缺口，继续安全合成部分结果；仍受整个
Chat 硬超时约束。可选评估最多等待 8 秒，按剩余总预算为最终合成预留 5 秒；
预算不足时跳过评估、保留缺口。日志只记固定事件、请求 ID 和异常类型。
结构化 gap 容量为 400，对应初始加最多三轮补充、每轮五任务、每任务二十缺口，
不因同文案跨任务独立编号而导致原本合法的输入溢出或静默遗漏缺口。

## 证据边界与后续

自然语言要求的满足性由独立模型语义评估，不是确定性或形式化事实证明；引用
绑定只能证明来源，不证明每一句判断成立。模型仍可能误判相关性、时间或对象。
后续可为支持结构化验收的能力引入可信对象绑定与受限谓词校验；不以关键词、
置信度或任意证据存在代替满足性。不改变统一 Capability 链路或写死问题类别。

本轮离线回归与本机部署结果记入 `progress-v1.md`；真实模型验收应单独注明，
不能把受控模型测试称为真实语义质量保证。
